# Engine module

## Orbital travel prototype

CircularOrbitalEphemeris derives deterministic circular coplanar planetary motion from campaign time and HohmannCoast evaluates the analytic coast. OrbitalTravel plans frozen escape, capture and approach budgets. OrbitalFlightProcessor advances atomic funded events in the power tick, preserving gravity-driven coast after missed capture. OrbitalPowerAccounting and OrbitalFuelAccounting share bounded forecasts, auxiliary checks and actual loaded-mass consumption. Save version 41 retains parking altitudes and orbital state through station, construction, household and fleet copies. Trade arrival checks and costs use the same projections. Geometry, paid voyage, thermal voyage, persistence, cancellation and organization tests cover the prototype. See [OrbitalTransfers.md](../OrbitalTransfers.md).

OrbitalTradeAuditTest reproduces fourteen paid mixed-cargo scenarios and writes `target/orbital-trade-report.md`. It compares real ticks with replacement-cost quotes, retains unused purchased propellant as inventory and verifies automated rejection of fuel losses even with full tanks. [OrbitalTradeReport.md](../OrbitalTradeReport.md) separates route cargo accounting from voyage consumption economics and records launch-window and reserve sensitivity.

OrbitalJourneySnapshot derives immutable presentation points and maneuver timing from the saved flight. It reconstructs both moving endpoints from frozen orbital parameters and retains actual ballistic position after failed capture. The frontend samples this bounded DTO on its preview worker. OrbitalJourneySnapshotTest verifies waiting, inward and outward capture, failed arrival and immutable collections.

ParkingOrbitTravel plans same-planet circular parking transfers using actual altitude, planetary gravity, main fuel, reactor feed and finite-burn limits. OrbitalFlight supports three-event transfers and one-event equal-altitude approaches; all event iteration follows the saved count. Save version 42 retains these semantics and existing copy paths preserve budgets. ParkingOrbitTravelTest covers paid outward and inward travel, forecast/tick agreement, failed circularization, docking, undocking, reload and one-event fleet organization. See [ParkingOrbitTransfers.md](../ParkingOrbitTransfers.md).

OrbitalBody resolves planets and their actual moons. LunarTransferComparison computes phase-aligned parent-centered coast and lunar gravity-well budgets. OrbitalTravel shares the funded event and power path with existing planetary journeys while ParkingOrbitTravel uses the selected body's own gravity and sphere. Save version 43 retains explicit gravity frames with legacy defaults. Lunar geometry, paid voyage, failure, cancellation, persistence and fleet organization tests cover both directions. LunarTransferAuditTest writes a 216-row catalog comparison to `target/lunar-transfer-report.md`. See [LunarTransfers.md](../LunarTransfers.md).

LunarTradeAuditTest writes `target/lunar-trade-report.md` from 26 paid mixed shipments and separately checks automated fuel economics, partial sales, reload and real lunar-port replenishment. TradeLegReadiness preserves the actual orbital rejection reason, including finite-burn limits. See [LunarTradeReport.md](../LunarTradeReport.md).

StagedLunarTradeAuditTest writes `target/staged-lunar-trade-report.md` from eighteen paid low-orbit access and lunar shipment probes. All reach a 2,000 km Earth depot from 500 km parking; fourteen buy depot cargo and complete lunar sales. Both active legs survive reload and separate checks validate automatic next-leg fuel purchases, inaccessible remote stock and depleted depot rejection. Full journey economics include access fuel alongside the lunar leg. See [StagedLunarTradeReport.md](../StagedLunarTradeReport.md).

IntermediateTradePlanner adds bounded one-stop lookahead for empty single-ship roaming traders at parking ports. When no direct profitable shipment exists, it evaluates up to eight operational ports on the same body using projected funded arrival and the actual arrival turn. Combined profit includes consumed access fuel; only current-port supplies and the first leg commit. The persisted REPOSITIONING phase moves the route origin only after actual docking and rechecks direct trades against live depot markets. Cancellation stops onward loading and failed maneuvers report interruption. StagedLunarTradeAuditTest covers lifecycle, economics, stock, cash, cancellation, reload, direct-trade preference and stable candidate ordering.

## Engine module rules

- All assignments (e.g., scientists, fleets, resource allocations) must be strictly validated against live model data before they change the engine state.
- Keep data models decoupled from visual frameworks. No `javafx.*` or `com.almasb.fxgl.*` imports allowed in this package.

This module contains the core game logic, the static data model and state management for the Space Conquest Game.

## Key components

- `LocalSiteGeometry`, `LocalSpaceTravel`, `LocalFlight` and `LocalFlightProcessor` plan and advance physical space-to-space journeys with frozen geometry, funded burns and actual ballistic drift. Save version 39 retains local state separately from queued crossings. `LocalSpacePowerForecast` uses the same burn/coast phases and daily remainder as ticks. Stationary departures conserve fuel within the earliest funded arrival tick. Recovery plans from current position and velocity; organization copies partition local budgets. Surface transfers and older prepaid itineraries retain compatibility behavior. See [LocalTravel.md](../LocalTravel.md).
- `PassengerTransitProcessor.canSustainJourney` checks every booked fleet member's species-specific supplies against actual scheduled days. Daily consumption remains tick-owned and continues during interruptions. Valid stasis avoids nutritional consumption but requires research and pod capacity. Existing cargo and passenger manifests preserve remaining stock through save/load.
- `RoamingTradePlanner` selects optional next-port trades from isolated paid shipment previews. `RoamingTradeCost` prices consumed physical fuel and electricity at the source port and ranks expected profit per actual planned travel day. `TradeShipmentSizing` searches smaller funded quantities and `TradeBasketPlanner` considers several goods sharing one destination and physical voyage budget. Roaming routes choose a new origin only after selling every lot and wait when no candidate is viable. Fixed-origin routes retain their return behavior. Save version 38 stores per-material `TradeCargo` manifests alongside mode and decision messages; older single-good routes reconstruct their manifest from legacy fields.
- `TradePortMaintenance` targets a provisional 60-day stationary electrical reserve at an active trader's actual port using physical stock and owner funds. Bounded partial purchases and compatible reactor fallback improve drought resilience while leaving main propulsion reserves protected. `LogisticsProcessor` moves dispatched routes behind waiting routes to share replenished stock. Per-material partial sales, cargo loss and corporate inventory valuation preserve each paid cost basis. `TradeReliabilityAuditTest` exercises nine 360-day scenarios and writes `engine/target/trade-reliability-report.md`; the recorded results and limitations are in [TradeReliabilityReport.md](../TradeReliabilityReport.md). `TradePropulsionAuditTest` adds six catalog and actual paid production probes, recorded in [TradePropulsionReport.md](../TradePropulsionReport.md).
- `TradeLegReadiness` checks an automated carrier's next port leg, retains destination approach fuel and buys current-port supplies only when the complete leg remains safe. `FleetPortReadiness` reports aggregated compatible refill stock without reserving or purchasing it. Profitable market selection prefers stocked ports. `FlightFuelLimits` stops sublight and replacement thrust at actual propellant exhaustion while preserving ballistic motion. Fixed-route empty returns use the same complete local supply gate. Safe multi-day local departures retain optional paid top-ups only when they reduce scheduled days. TradeArrivalReadiness requires carried 60-day stationary electricity after complete port departures when destination refill stock is insufficient or scheduled travel exceeds two days. Short stocked trips retain 48 hours and committed approaches keep their existing gate. Queued crossings use post-maneuver electrical stores consistently with previews. Return readiness is advisory and never required for the next leg. See [FleetSupply.md](../FleetSupply.md).
- `ShipSupplyCatalog` and `ShipSupplyState` separate compatible bulk supplies from cargo and working tanks. Supplies add travel and launch mass, survive ship copies and persist in save version 37. `FleetSupplySimulation` and `FleetSupplyForecast` coordinate bounded coasting delivery events with electrical accounting and braking checks. Cryogenic containment outages produce physical boil-off. See [FleetSupply.md](../FleetSupply.md).
- `JourneyPropulsion` freezes each physical itinerary's selected drive, effective exhaust velocity, reactor feed and committed feed quantity. Movement, interruption and fleet membership copies retain it; recovery and rescue replace it with their new selections. Save version 37 retains these values and scheduled electrical deliveries use them for fission and fusion braking checks.
- `FleetPropulsionSupply` advances bounded power and motion phases through combined electrical, propellant and reactor feed schedules. `FleetSupplyTimeline` preserves original delivery times after replanning. `FleetSupplyReplanning` retains current speed and saved exhaust, calculates post-transfer braking and pays additional nuclear feed from carried cargo. Preview and tick checks protect stock, capacity, later deliveries, stopping distance and arrival reserves. `FleetReturnReserve` forecasts destination stores and an immediate direct return without changing state.
- `FleetFuelSharing` builds immutable multi-ship transfer previews and applies only the reviewed allocation after live revalidation. It protects supplier propulsion, preferred drive reactor feed, electrical arrival reserves and drifting recovery. See [FleetSupply.md](../FleetSupply.md).
- `FleetOrganization` changes fleet membership without altering ships or paid movement state. Mixed combat and civilian groups share orders and physical sublight travel uses their limiting acceleration and fuel-supported peak speed. Splits partition per-ship budgets and inherit active motion; joins require shared sites, identical journeys or verified coasting contact. Active rescue membership and conflicting trade routes are protected. See [Fleets.md](../Fleets.md).
- `RescueStatus` preserves the latest approach, delivery, missed contact, transfer rejection or power failure for donor and receiver within their immutable power snapshots. Every electrical copy retains it and save version 37 persists it. `FlightRecoveryReadiness` explains the live physical and electrical recovery gates without changing reserves.
- `RescueRendezvous` plans bounded analytic interception from system space or a trailing drift position, reserves an explicit payload and verifies velocity-matched contact after all power/motion updates. A pending `RescueOrder` lives in the persisted `FlightMotion.Trajectory`. Supplies transfer once; onward recovery remains separately validated. Rules and exclusions are recorded in [RescueRendezvous.md](../RescueRendezvous.md).
- `ShipArrivalReserve` checks 48 hours of essential services and cargo demand. Known local destinations use an eclipse-first sunlight cycle; interstellar and unknown arrivals retain darkness. Charge/discharge limits and daily charging counters remain enforced. Stasis scales with pod occupancy and cargo preservation scales with weighted vulnerable mass under the blueprint's captured power ceiling.
- `CargoDeterioration` applies provisional material-specific grace periods and fractional daily losses from the final cargo power deficit. `CargoPreservationState` saves cumulative exposure by cargo pool and last-tick physical losses. Powered ticks stop losses without resetting exposure. `LogisticsProcessor` reconciles missing freight and writes off its paid cost without a second cash charge or claimed delivery.
- `ShipSupplyTransfer`: Atomically moves same-owner ship cargo or compatible tank reserves into electrical fuel stores, propellant tanks or drive reactor cargo at a shared stationary site. Mixtures require both ingredients and receiver capacity. Interrupted local departures with zero progress can receive supplies. `RescueRendezvous` permits supplies at coasting contact after a same-owner sublight intercept; mid-transfer local and warp rescues remain future work.
- The provisional ship power catalog includes researched solar arrays, chemical auxiliary generators, fission reactors, batteries and dedicated generator/reactor storage. New player and corporate blueprints capture their electrical profiles. `ShipPowerProcessor` accounts for real fuel, charging losses, eclipses, phase-specific drive loads and electrical shortfalls. `ShipPowerForecast` checks local and crossing budgets plus a 48-hour essential and cargo arrival reserve without simulating every voyage day. `ShipLocalPowerForecast` skips stable daily illumination cycles between generator-feed exhaustion and battery boundaries; bounded conservative rejection protects unsupported cycles. `ShipSolarEnvironment` permits solar during local space travel and suppresses it during atmospheric surface transfers and interstellar crossings. Legacy blueprints retain explicitly identified electrical compatibility behavior.
- `SolarRadiation` shares relative stellar luminosity divided by squared distance in AU across ship arrays, planetary solar plants and station `SOLAR_ARRAY` modules. Moon distances use their parent orbit. Closer arrays can exceed their 1 AU reference output and distant arrays have no artificial minimum generation. Strength follows the generator's provisional mass/type relation. Unspecified system-space locations use the outermost known orbit with a 1 AU baseline. Generic station `POWER` modules retain their existing source model.
- `ShipPowerResupply` buys compatible electrical fuel atomically from a local hub. `ShipBatteryCharging` withdraws real stored grid energy, charges its buyer and credits the grid owner. `ShipPowerSurvival` applies provisional passenger outage grace and loss rates. Electrical state, profiles and pending rescue trajectories persist in save version 37.
- `FlightMotion` and `FlightRecovery` retain sublight position and velocity at the first electrical failure, coast without free thrust and plan replacement accelerate/coast/brake trajectories from current motion and remaining reserves. Tick processing stops every fleet ship at the earliest failure and conserves unused drive energy. Recovery requires physical propellant, electrical endurance and a reachable destination. One-dimensional drift and recovery persist through save/load; gravity, lateral navigation and return after overshoot remain future work.
- `PausedTravelRecovery` validates a new physical local trajectory from saved drift or preserves the powered fraction of older abstract local and warp progress. Older local resumption reuses prepaid maneuver fuel without another launch payment. Warp retains corridor progress and checks live research. Recovery previews include the remaining local leg, any queued crossing and essential arrival reserves. Arrays may recharge an interrupted fleet while actual physical drift continues. Exact orbits and warp re-entry remain provisional.

## Physical units and standard measurement system
All simulation mechanics, celestial data definitions and calculations standardize on the International System of Units (SI) to prevent unit conversion discrepancies across subsystems:
- **gravitational acceleration:** Measured in meters per second squared (m/s²). Earth standard gravity is 9.81 m/s², while species preferred gravity and celestial body surface gravity use this unit directly.
- **mass:** Measured in kilograms (kg). Spaceship dry mass, loaded cargo, material stockpiles and resource yields use kilograms.
- **force and thrust:** Measured in Newtons (N). Propulsion outputs, thruster ratings and launch force barriers use Newtons.
- **temperature:** Measured in Kelvin (K). Ambient celestial surface temperatures, thermal tolerances and atmospheric entry friction use Kelvin.
- **power and energy:** Measured in kilowatts (kW) and kilowatt-hours (kWh). Power generation, facility power draw and battery buffers use kilowatts.
- **distance and diameter:** Celestial diameters and orbital radii use kilometers (km); generated star system coordinates use light-years for interstellar distances.
- **pressure:** Measured in standard atmospheres (atm) or kilopascals (kPa) for planetary gas envelopes and atmospheric drag calculations.

## Conventions
- Game component properties should be read from resource files where practical. The current simulation still has hard-coded values and catalogs.
- Prefer immutable Java records for data models and snapshots. Current `GameState` nested collections are not all defensively copied and some live model objects are mutable.
- Create new snapshots with `GameState.builder()` and modify an existing snapshot with `toBuilder()` or a `with...` method. The removed partial positional constructors could silently discard newer fields.
- `DataModelLoader` caches loaded lists; call `DataModelLoader.clearCache()` to force a reload.
- unknown JSON properties are ignored, so data files can be extended before the records are updated.

## Current integration gaps

- Completed application research retains a pending outcome. Optimized success permits a path choice; other outcomes can be accepted or discarded. Accepted modifiers accumulate across 500-point refinement cycles and application complexity is floored at 1. Each recorded outcome can be resolved once. Legacy researched applications retain baseline path switching until they complete a recorded refinement. Facility throughput, power generation and new construction quotes use accumulated modifiers. Extra batches consume full recipe inputs and finite deposits. Specialized facility capacity starts at the application's baseline complexity and gains one per tier under `facility_manufacturing_limits.json`; insufficient capacity pauses output and fuel demand. New public, tile and corporate projects quote the minimum required tier. Existing project quotes remain fixed.
- `ShipApplicationProduction` links seven main drives, the designer's reactor, cargo vaults, corporate cargo holds and stasis pods to applications. New blueprints freeze thrust, net power balance, cargo and stasis capacities, complexity and a mass-weighted cost multiplier. Legacy stasis blueprints retain 100 passengers per pod. Corporate procurement selects a researched chemical or fission drive and reuses its frozen blueprint quote. Yard selection and daily construction enforce resource-configured complexity limits. Component stats, specialized factory limits and generic material bills remain provisional; other future component catalogs and research-dependent nanotechnology tiers are not implemented.

- Generated campaigns use the starting era's calendar and opening economy. The no-argument engine constructor starts with no world; `SpaceConquestEngine.fromSolScenario()` explicitly loads the preserved static Sol fixture. Public facilities receive opening operating capital from their empire, then keep their own sale revenue and pay wages, inputs, fuel, power and maintenance; opted-in loss-making facilities may receive local infrastructure and industry support. Power plants deliver measured grid electricity and industrial households need electricity as a tier 1 good. Industry pays for powered shifts before production. Stored battery electricity has no owner ledger and is not billed yet. Cargo terminals provide rocket lift using purchased RP-1 and liquid oxygen, mass-driver facilities lift goods using available power and elevators lift goods or ships carrying passengers. Provider throughput resets each daily turn. Mass drivers and elevators reserve one hour of power per launch; their prepaid generator-backed electricity is settled through the daily grid and corporate launch earnings enter profit tax. The terminal is distinct from `CommercialHub`. Facility types and refinement recipes do not yet share one application catalog.
- Local industry and household purchases do not pay a transport charge, and same-body industry sales do not pay a gross transaction tariff. VAT is unimplemented. `CorporateProfitTaxProcessor` assesses realized profit across each corporation's facilities, space elevators and assigned trade routes after carried losses and records unpaid tax on the corporation's persistent tax account; paid tax enters a populated local municipal account. Mining and other fleet income are not included yet.
- `SpaceConquestEngine` owns the live world collections and runs the turn processors. `GameState` is the transfer shape, but it is not yet a fully isolated immutable snapshot. `applyGameState` restores couriers and local and imperial balance sheets.
- Market demand is refreshed from current residents and active recipe inputs before price processing, system budgets, household purchases, material industry transactions and municipal accounting. `CitizenCohort` and `ColonyDemographics` are derived for the household pass but are not persistent; `PopulationProcessor` still updates the older age-group model. Household accounts persist filled jobs, unemployment pressure, material and electricity coverage, rolling wellbeing and annual shortage stress. Basic shortages reduce survival and births at the annual demographic update. Household purchases deplete market supply and fund hub purchases from producers. Opening and retail stock have no seller identity. Explicit healthcare, detailed qualifications and wage competition remain future work; household profession shares persist and unemployed workers retrain gradually for funded vacancies.
- `WarpNetwork` pathfinding is not used for ordinary fleet movement. After daily movement and passenger arrival, idle fleets at the same site in the same system engage when their empires are at `TOTAL_WAR`. The engine delegates through `FleetEncounterResolver`; the current `TacticalFleetEncounterResolver` uses `TacticalCombatProcessor` provisionally and can be replaced during the planned combat overhaul. Surviving ships replace the live fleets, empty fleets are removed and compact `FleetEngagementRecord` entries persist in `GameState` and saves (latest 1,000). This does not yet use fleet stances, player orders or the warp network to select targets. Generated anomalies are not passed into the normal sensor turn.
- Corporate investments create corresponding world entities. New factories begin as tier-zero construction sites and complete after 500 work hours of daily project progress; corporate ship orders wait for daily work and material purchases at their selected ground or orbital yard. Ground shipyards are dedicated `surface_shipyard` facilities, separate from commercial hubs that provide materials. Yard output is limited by modules, technology and actual payroll staffing for surface facilities. Generic bills also gate stations, elevators and megastructure stages. Ground projects consume stock only from their own body's hub. Space projects consume stock from a station hub at the build site or from an owner's cargo or construction ship at that site. Cargo loading buys from a source body's hub and pays an available launch provider. Fleet locations distinguish surface, orbit, dock and deep-space sites with daily local journey progress. Explicit offworld passenger bookings remove residents from the source population and keep a ship manifest until arrival at the named surface destination; free seats do not attract passengers. Automated routes require an owned cargo ship, buy stock from the origin hub, carry it aboard and sell it on arrival to a destination hub with sufficient cash and storage. Routes buy local-maneuver fuel at an accessible hub when needed and include that purchase in daily operating results. Route results also account for cargo purchase, launch cost, wholesale sale and configured destination tariff. Paid cargo aboard a route contributes to corporate book net worth. Local travel time and maneuver requirements remain provisional; component-level receipts and crew remain unimplemented. Automatic corporate fleet arbitrage and mining income were removed because they created credits without paid transactions or extraction. Stock ownership, dividends and capital issuance are future work.
- The old list-only `LogisticsProcessor.processTradeRoutes` overload remains deprecated for compatibility tests. It is not called by the game tick and still computes instant transfers if invoked directly.
- Terraforming projects now buy physical inputs before daily progress, but the resulting atmospheric composition is still recalculated in the processor and not persisted in `GameState`.
- `SaveGame.fromGameState` and `SaveGame.toGameState` map all current snapshot fields, while the calendar and speed remain separate save metadata. The data model table describes intended runtime and save ownership, although not every newer live field is covered by the save format. System debt is an aggregate of local debt and has no separate ledger.

PlanetaryTransferComparison is a read-only circular coplanar Hohmann benchmark. It returns immutable orbit and ship-budget records with launch-phase wait, 500 km parking escape/capture, protected main reserves, propulsion feed checks and a provisional finite-burn criterion. It cannot create a travel order or mutate supplies. The 72 catalog probes and model limitations are recorded in [PlanetaryTransferReport.md](../PlanetaryTransferReport.md).

PlanetaryTransferComparison also accepts explicit departure and arrival parking altitudes and rejects parking beyond the approximate planetary sphere of influence. The parking/tank audit rebuilds each candidate through ShipBlueprintFactory, includes full tank wet mass and scaled main reserves and distinguishes valid blueprints from oversized ones. See [ParkingOrbitTankReport.md](../ParkingOrbitTankReport.md).

ChemicalFreighterCatalog registers the live 2,500 kg hold and 120,000 kg conditioned tank with research and mixture-volume checks. MainTankThermalLoss runs once at the end of daily power resolution before rescue completion, removing proportional main mixture during essential-power outages. It preserves freight and dedicated supply stores. No new saved fields are required. See [ChemicalFreighterDraft.md](../ChemicalFreighterDraft.md).
